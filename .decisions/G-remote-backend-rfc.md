# RFC: backend remoto multi-proyecto de Climier

- Gate: `G-remote-backend-rfc` · Iniciativa: `remote-backend` · Estado: borrador
- Autor: orchestrator · Fecha: 2026-09-24

## Problema

Climier guarda hoy el DAG bajo `$CLIMIER_HOME/projects/<project_id>/tasks.json`; compartir `.climier.json` entre máquinas no comparte el estado ni los locks. Los equipos necesitan que varios clientes y worktrees coordinen contra un Climier alojado en otra máquina, que una misma instalación del servidor gestione más de un proyecto, y una forma explícita de importar/exportar el DAG completo entre el almacenamiento local existente y el remoto.

La UI server existente no cubre ese caso: sirve una proyección de solo lectura para un proyecto local, escucha en loopback y no ofrece autenticación. El `project_id` identifica el estado, pero no autentica al actor ni configura un backend. El usuario dispone de una máquina accesible mediante SSH agent y Tailscale para una primera prueba de extremo a extremo; esa forma de acceso debe servir para validar el despliegue sin convertirse en dependencia del protocolo ni impedir después un host cloud.

## Propuesta

Agregar un modo remoto explícito, seleccionado por configuración versionada en `.climier.json`. En modo local (configuración ausente) el CLI conserva su comportamiento actual. En modo remoto, el servidor es la única autoridad del estado para las operaciones normales; el cliente no mantiene una copia mutable local ni sincroniza DAGs implícitamente. Dos comandos deliberados de transferencia, `push` y `pull`, permiten copiar el DAG completo del proyecto entre local y remoto, con protecciones ante reemplazos y reportando claramente el sentido y resultado de la transferencia.

La implementación se validará primero contra el host Linux del usuario, accesible mediante Tailscale y SSH agent. El SSH agent puede usarse para desplegar/administrar el servicio o abrir un túnel durante la prueba, pero el cliente Climier debe hablar un protocolo de aplicación remoto estable (HTTP(S)/API tipada); SSH no será el contrato de almacenamiento ni un transporte obligatorio. URL, autenticación, protocolo y catálogo de proyectos permanecen independientes de que el proceso se ejecute en esa máquina, en una VM o posteriormente en cloud. No introducir dependencias de rutas de home, nombres de host Tailscale, scripts de login o claves privadas específicas del usuario en el producto.

Configuración ilustrativa, sujeta a la decisión del ADR:

```json
{
  "version": 1,
  "project_id": "b4e2c579bbb81669",
  "backend": {
    "type": "remote",
    "url": "https://climier.example.com"
  }
}
```

El `project_id` se conserva como identidad estable del proyecto a través de worktrees y máquinas. El servidor debe poder alojar y aislar muchos `project_id`; trata ese valor como identificador opaco y lo resuelve mediante catálogo/registro server-side a un directorio confinado bajo la raíz de datos configurada. Nunca concatena entrada del cliente como path ni permite traversal o colisiones; identidad desconocida o sin permiso se rechaza antes de abrir storage. Sin `backend` se mantiene el backend local existente. `.climier.json` declara un solo endpoint remoto por proyecto en v1; `push`/`pull` conectan la copia local de ese `project_id` a ese endpoint, no configuran múltiples destinos. Las credenciales no se guardan en el archivo versionado: el cliente las obtiene de una fuente local/secreta (por ejemplo `CLIMIER_TOKEN`), pendiente de fijar en el ADR.

La recomendación es que el servidor ejecute las operaciones canónicas de Climier con la misma lógica de providers y kernel, y persista los estados en su propio almacenamiento local por proyecto. El protocolo remoto debe ser una fachada tipada sobre operaciones core, no un endpoint genérico de lectura/escritura de archivos ni una exposición directa de `ui/server`. Así el servidor conserva el lock/transaction boundary que hoy garantiza claims exclusivos y commit atómico de estado más log.

En el cliente, una única fachada de backend de proyecto, llamada por adapters de CLI y APIs/host de plugins antes de tocar estado, selecciona el backend local (kernel/storage actual) o remoto (API HTTP(S)). Los providers y el kernel no se vuelven transport-aware: el servidor invoca su kernel local; el routing pertenece al límite del cliente entre application/adapters y ejecución del backend. Todas las lecturas y mutaciones deben pasar por esa fachada para evitar accesos locales accidentales cuando `backend.type` sea `remote`.

El contrato de comandos remotos de v1 es:

| Superficie | Backend remoto v1 | Si no está soportado |
|---|---|---|
| Lecturas built-in del DAG (`status`, `context`, `show`, `history`, `search`, `initiatives`, `log`, `state`) | API remota; read-model común | `REMOTE_UNSUPPORTED_OPERATION` con envelope JSON común; nunca leer local como fallback |
| Mutaciones built-in del DAG/lifecycle, lifecycle administrativo y operaciones core/batch | API tipada; operación canónica validada por kernel server-side | `REMOTE_UNSUPPORTED_OPERATION` con envelope JSON común; nunca mutar local |
| `init` | Provisiona/inicializa el `project_id` remoto solo con autorización explícita | Falla sin crear estado local paralelo |
| `push` / `pull` | Transferencia puntual entre backend local y remoto configurado; ver semántica abajo | Falla sin cambios parciales |
| `transfers` / `transfer-status` | Lista journal local de transferencias pendientes y consulta el resultado por `transfer_id`; consulta el registro server-side para push o el marker atómico local para pull | Error estructurado de transferencia no encontrada; nunca infiere éxito por timeout |
| `snapshots` / `restore` | No soportados en la primera versión remota | `REMOTE_UNSUPPORTED_OPERATION` |
| UI (`climier ui`) | Sigue local-only en v1 | `REMOTE_UNSUPPORTED_OPERATION` si el proyecto activo está configurado remote |
| Plugin APIs/CLI (`api.core.run`, query, plugin-data y comandos de plugin) | `api.core.run` solo para operaciones core tipadas incluidas explícitamente en el protocolo | Query, plugin-data y comandos/extensiones de plugin devuelven `REMOTE_UNSUPPORTED_OPERATION`; no cargar plugins locales como autoridad remota |

La fachada vive en el cliente, en el boundary de aplicación/adapters antes del kernel/storage local; los providers y el kernel no se vuelven transport-aware. El servidor recibe operaciones tipadas y ejecuta el kernel/providers/storage localmente. Las extensiones de plugin instaladas en el cliente que no pasen por operaciones core remotas no pueden actuar sobre el proyecto remoto; las policies/plugins de autoridad se provisionan y ejecutan en el host server-side.

`push` y `pull` son transferencias de snapshot completo, no sincronización bidireccional ni merge automático. Se invocan en un checkout cuyo `.climier.json` nombra explícitamente el remote destino/origen. `push` lee la fuente local existente en `$CLIMIER_HOME/projects/<project_id>/tasks.json` y escribe el remoto configurado; si esa fuente falta, devuelve `LOCAL_STATE_NOT_FOUND`. Si el `project_id` aún no está registrado en el servicio, `push` puede provisionarlo únicamente con permiso explícito de creación de proyecto; sin ese permiso no cambia ningún estado. `pull` lee el remoto configurado y crea o reemplaza la copia local en esa misma ubicación; si no hay remoto configurado, falla con `REMOTE_NOT_CONFIGURED`. Estos comandos son los únicos que acceden explícitamente a la copia local cuando el proyecto está configurado con backend remoto; ninguno cambia la configuración ni el backend activo del checkout. Son excepciones explícitas al routing remoto normal, no fallback implícito.

Por defecto, ambos comandos solo crean una copia si el destino está ausente, o reconocen como no-op una copia semánticamente idéntica. El destino remoto está ausente si el servidor aún no tiene registro/state para el `project_id`; está prístino si su state validado tiene `nodes={}`, `edges=[]`, `initiatives={}`, cero entradas de log y revision 0. El destino local está ausente si no existe su `tasks.json`; un `emptyState()` recién inicializado o cualquier state con log/revision cuenta como existente, aunque no tenga nodos. Un primer `push` a un remote prístino vacío es create-only condicionado por la revisión remota observada (0 si ya fue provisionado por `init`, `absent` si no existe); no requiere `--overwrite=true`. Un `pull` a destino local ausente es igualmente create-only con CAS `absent`. Todos los demás destinos existentes que difieran requieren overwrite explícito, incluyendo un state local inicializado aunque no tenga nodos y DAGs vaciados que conserven log/revisión. El replace no se considera una mutación ordinary del DAG; aplica la transacción de transferencia y audita el reemplazo. El overwrite requiere `--overwrite=true` y una precondición CAS explícita (`--if-remote-revision N` para `push`; `--if-local-revision N` para `pull`, y `absent` para indicar explícitamente que no existe destino local). Para `push` a un `project_id` remoto aún no provisionado se requiere `--if-remote-revision absent` junto con permiso explícito de creación; si ya existe, siempre se pasa su revisión numérica actual. Para el primer push a un remoto prístino creado por `init`, se pasa la revisión global existente (normalmente 0) y se usa el create-only permitido mientras el destino siga vacío. La precondición se compara y el commit ocurre bajo el lock del destino. Cuando el destino está ausente/prístino y no hay overwrite, es una operación de create-only/CAS-absent; un destino que deja de ser prístino antes del lock causa `REMOTE_CONFLICT`. La fuente se captura como snapshot consistente y se envían exactamente su revisión/hash; una mutación posterior de la fuente pertenece a otra revisión y no modifica ese payload. Cualquier transferencia se rechaza si el snapshot fuente capturado contiene claims activos o tareas `in_progress`; el overwrite también se rechaza si el destino actual bajo lock los contiene. El estado entrante pasa validación completa de schema/protocolo antes de mutar. `pull` instala el snapshot mediante operación del kernel/lock local y conserva atomicidad de estado+log; `push` hace lo mismo en el server bajo su kernel/lock.

Se preserva el historial de auditoría previo del destino y se añade un evento de transferencia con dirección, origen, hash/revisión fuente y revisión previa/nueva del destino; el log fuente completo se conserva como payload namespaced dentro de ese evento y no se reinyecta como entries de primer nivel. Repetir el mismo `transfer_id` y hash fuente devuelve el resultado previo sin re-aplicar ni duplicar auditoría. Si el hash fuente ya coincide en destino con otro `transfer_id`, es un no-op semántico y la respuesta informa `overwritten:false` y revisiones antes/después iguales.

La transferencia es una operación dedicada del kernel, no el `stateOperation` genérico: bajo el lock del destino compara CAS, valida, aplica rebase y registra evento/fingerprint de transferencia junto al state en una sola escritura atómica. Así no se pierde el fence por la normalización genérica de revisión de state operations. Para impedir ABA/CAS obsoleto, la transferencia verifica bajo lock que los states fuente y destino estén activos y consistentes con sus respectivos ledgers; una fuente o destino con generación ausente/distinta falla con `STATE_FENCE_REGRESSION` y requiere recuperación local explícita, no se usa transfer como bypass. Calcula `F = max(source.state.revision, destination.state.revision, H_destination, maxNodeRevision(source), maxNodeRevision(destination)) + 1`, escribe `state.revision = F` y asigna `revision = F` a cada nodo entrante. El payload/hash de transferencia excluye el `fence_generation` y metadatos locales del source; el commit conserva los datos del DAG, log/auditoría y marcador de generación del ledger DESTINO, nunca importa el marcador de otro proyecto/backend. La fuente se captura solo si también satisface su ledger.

El kernel centraliza en un helper la asignación de revisiones compartido por provider mutations, batches y transferencias: nodo nuevo recibe al menos `state.revision + 1`; nodo modificado recibe `max(prevNode.revision + 1, state.revision + 1)`; el state revision efectivo avanza al menos hasta la revisión máxima asignada. El preview usado por cada paso interno de `core.batch` y el diff final deben invocar la misma regla, de modo que ningún CAS dentro del batch use una revisión distinta de la que se persiste. La nueva semántica requiere versionar el state y migrarlo bajo lock antes de habilitar operaciones con fence; el protocolo server/client también valida compatibilidad antes de operar. Estas reglas invalidan `if_revision`/`if_revisions` viejos incluso si un ID se elimina y reaparece. Tests cubren provider, batch, migración, nodo presente, eliminado/recreado y CAS global/nodo capturados antes de push/pull.

El bump de versión no basta para protegerse de clientes antiguos: una ruta previa de `restore` puede capturar `CLIMIER_INCOMPATIBLE_VERSION`, comprobar solo que el archivo existe y escribir un snapshot legacy sobre el state nuevo; `init --force` antiguo también puede reemplazarlo. Cada proyecto sujeto al fence mantiene un ledger de revisión alta y generación fuera de `tasks.json` y snapshots, en un archivo reservado dentro del directorio de storage que contiene el state file canónico (local) o dentro del directorio resuelto por el catálogo confiable (server); ambos usan el mismo `.lock` por proyecto. El state incluye un `fence_generation` opaco que debe coincidir con la generación del ledger. La migración inicial bajo lock desde un state pre-fence calcula `H = max(state.revision, maxNodeRevision(state))` y `F = max(H, state.revision, maxNodeRevision(state)) + 1`; calcula determinísticamente el state destino con `state.revision = F`, `revision = F` en todos los nodos y generación propuesta, y persiste atómicamente un registro de ledger `migration_pending` con H, F, generación propuesta, schema origen, SHA-256 de bytes exactos del state fuente y SHA-256 exacto del state destino. Solo tras confirmar durablemente ese registro escribe el state destino y luego finaliza el ledger como activo y consume la intención. Al reanudar, si el state actual coincide con el hash fuente, repite la escritura del destino; si coincide con el hash destino y generación propuesta, finaliza el ledger; cualquier otro contenido o versión falla cerrado. Así el crash solo auto-reanuda el cambio determinístico ya comprometido, sin aceptar un state legacy modificado. Todos los CAS globales y por nodo capturados antes del fence dejan de coincidir incluso tras crash/resume. Un crash antes de persistir `migration_pending` no ha iniciado migración fenced y puede reintentar desde el state pre-fence intacto; después de persistirlo, se aplican estas reglas exactas. Solo esa migración inicial puede crear ledger/intención; una vez hay ledger, todo writer compatible compara la generación/schema del state persistido con ledger antes de migración, precondición o CAS. State sin marcador o con generación distinta indica `STATE_FENCE_REGRESSION`, aunque el scalar global sea mayor o igual a H. La única excepción de auto-resume es una intención `migration_pending` cuya huella y schema coinciden exactamente con los bytes actuales del state: entonces repite idempotentemente la migración; si el state ya lleva la generación propuesta, valida el resultado y finaliza el ledger. Si no coincide exactamente, falla cerrado y exige recuperación compatible explícita. Al terminar con éxito la migración se elimina/consume la intención pendiente mediante actualización durable del ledger, así un snapshot v4 o `init --force` de un CLI antiguo posterior no puede volver a clasificar como migración el mismo state sin marcador. Esto distingue un crash de un downgrade posterior y cubre incluso commits legacy que eleven otra vez la revisión global. El ledger y su generación no forman parte del DAG transferido y nunca se importan, restauran ni borran mediante `push`, `pull`, snapshots, `restore` o `init --force`. Toda ruta de escritura compatible —mutaciones de provider, batch, state operations, bootstrap/recovery, transfer y cualquier helper de storage que escriba el state— debe pasar por una primitiva común de commit con fence: verifica ledger/generación/revisiones, reserva antes de escribir un high-water que nunca disminuye y persiste state+log atómicamente. El ledger se actualiza durablemente con temp en el mismo filesystem, flush/fsync, rename atómico y sincronización del directorio antes del rename del state. Si el proceso cae tras reservar H y antes de escribir state en un commit ordinario, el state conserva generación vigente; el siguiente arranque puede identificar la reserva por la misma generación y completar una recuperación idempotente sin evaluar CAS, rebasando global y todos los nodos al menos al high-water reservado sin reducir el ledger. State sin/diferente generación fuera de la única intención pendiente con fingerprint exacto nunca se auto-repara. El lock existente no auto-expira ni se roba: si una muerte deja `.lock`, el CLI devuelve timeout/fallo cerrado; un operador debe comprobar que el proceso dueño ya no existe y retirar manualmente el lock siguiendo el runbook, tras lo cual el siguiente comando compatible reanuda solo la migración/commit identificada por ledger. Nunca se elimina automáticamente un lock cuyo propietario pueda seguir vivo, incluso al reiniciar el servicio server-side. Si ledger se pierde, es ilegible o inconsistente, falla cerrado y exige recuperación administrativa desde backup confiable; nunca se reconstruye automáticamente desde un state posiblemente regresado. Tests fallan/reinician antes/después de escribir intención, reservar y renombrar state durante migración inicial y commit normal; comprueban auto-resume solo para baseline exacto, rechazo de restore/init-force legacy posterior aunque escale el scalar, y recuperación explícita que rebasa nodos/global antes de reabrir CAS.

Un `restore` local ejecutado por un cliente compatible valida snapshot legacy como datos, pero nunca reinstala sus revisiones ni generación: bajo lock calcula `F = max(H, current.state.revision, maxNodeRevision(current), snapshot.revision, maxNodeRevision(snapshot)) + 1`, asigna `revision = F` a todos los nodos restaurados y `state.revision = F`, conserva/estampa la generación local vigente y persiste por la primitiva fenced. `init --force` y recuperación de state corrupto también conservan ledger/generación y crean un state por encima de H. Si se detecta marcador/generación ausente o distinta —incluido restore v4 antiguo seguido de escrituras que eleven el scalar a ≥ H—, toda operación normal, CAS y `push`/`pull` falla antes de precondiciones; solo `restore` o `init --force` compatible puede reparar, rebasa global y todos los nodos por encima de `max(H, current, snapshot)` y estampa la generación local antes de volver a permitir CAS. La migración inicial interrumpida después de persistir `migration_pending` es recuperable idempotentemente solo si siguen presentes exactamente los bytes/schema legacy cuyo fingerprint está guardado; si `init --force` ya sustituyó ese state, no se promete recuperar los datos borrados y el operador debe elegir el reset explícito compatible. Un crash antes de persistir `migration_pending` deja la migración sin iniciar y permite el retry normal desde el state pre-fence intacto. Estos flujos no afirman que el schema impida escrituras directas de binarios antiguos en disco; el servidor sí rechaza protocolo incompatible, y el siguiente writer compatible los detecta/falla cerrado. Tests cubren push/pull entre ledgers independientes y preservación de generación del destino, restore de snapshot v4, restore/force-init legacy que eleva el scalar por encima de H y aún rechaza un CAS de nodo antiguo, reparación compatible, migración/commit con fallo y reinicio antes/después de persistir pending, reservar H y renombrar state.

Un conflicto, validación o fallo confirmado de escritura deja destino intacto; los errores incluyen dirección, código y revisiones esperada/actual cuando aplique. El cliente genera un UUID `transfer_id` y lo persiste en un journal local durable (dirección, project_id, destino, hash/revisión fuente y CAS esperado) antes de enviar. El servidor persiste `transfer_id` y fingerprint (`direction`, project_id, destination, source_hash, expected_revision) dentro del log/evento del mismo commit que instala un push; `transfer-status` busca en ese registro autoritativo. Pull persiste el mismo ID/fingerprint/resultado en el marker local que se instala atómicamente con state+log. Un UUID/fingerprint no se acepta como confirmado separado del commit del destino. Éxito marca completed, rechazo comprobado pre-commit marca failed, timeout deja unknown. Un mismo ID con fingerprint idéntico devuelve el resultado original sin volver a aplicar; con diferente dirección/proyecto/destino/hash/revisión esperada devuelve `TRANSFER_ID_CONFLICT`.

Un timeout después de un posible commit devuelve `TRANSFER_OUTCOME_UNKNOWN` con `applied: "unknown"`, nunca afirma `applied:false`. `climier transfers [--status pending|unknown|completed|failed]` lista operaciones del journal local del usuario; `climier transfer-status <transfer_id>` busca localmente y, para push, consulta el registro durable server-side; `climier push|pull --transfer-id <UUID>` reintenta exactamente el mismo snapshot solo si hash/revisión fuente siguen coincidiendo. El journal guarda el payload snapshot en blob local privado con permisos restrictivos hasta estado terminal, para que el reintento tras cerrar el proceso no dependa de que la source siga igual; `--transfer-id` nunca recaptura/reemplaza ese payload. El mismo request devuelve el resultado almacenado sin aplicar dos veces ni duplicar auditoría; un snapshot fuente distinto requiere un nuevo ID. El journal permite recuperar la operación luego de cerrar el proceso. Los subcomandos de recuperación no leen el DAG local como backend de proyecto; acceden solo al journal de transferencias y al endpoint configurado.

La respuesta JSON de éxito es `{ "transfer": { "transfer_id", "direction", "project_id", "source", "destination", "source_revision", "source_hash", "destination_revision_before", "destination_revision_after", "applied_revision", "overwritten" } }`. `destination_revision_before` es la revisión leída y comparada por CAS (null si estaba ausente); `destination_revision_after`/`applied_revision` es la revisión global escrita tras la transferencia. Los errores mantienen el envelope común `{ "ok": false, "error": { "code", "message", "details" } }`; `details` incluye `transfer_id`, `direction`, `project_id`, `applied` y, para conflictos, `expected_revision`/`current_revision`. Errores diferenciados incluyen `REMOTE_CONFLICT`, `SCHEMA_INCOMPATIBLE`, `CLAIMS_ACTIVE`, `REMOTE_UNAVAILABLE`, `AUTH_REQUIRED` y `PROJECT_FORBIDDEN`. Si el timeout ocurre antes de commit confirmado, `TRANSFER_OUTCOME_UNKNOWN` lleva `applied: "unknown"`; el cliente consulta/reintenta con el mismo `transfer_id`. Solo un rechazo verificado pre-commit afirma `applied: false`. Éxito confirma source/destination, hash y revisión aplicada. La credencial/configuración de destino no se copia al otro backend. La configuración de policies/plugins que afectan operaciones remotas es autoritativa en el servidor: los clientes no pueden enviar código/plugin arbitrario ni cambiar la policy efectiva del proyecto.

El servidor y el cliente deben definir errores estructurados compatibles con el contrato JSON actual, versionado/compatibilidad del protocolo y límites de tiempo/red. El actor `--as` permanece identidad de auditoría, nunca credencial. Toda ruta de proyecto exige autenticación y autorización asociada al proyecto; el transporte desplegado fuera de localhost debe usar HTTPS o terminar TLS en un proxy confiable. Las respuestas remotas no deben revelar paths del filesystem del servidor.

`init` en modo remoto nunca crea un DAG local paralelo. Solo puede provisionar storage/state ausente para un `project_id` previamente configurado en el catálogo confiable, cuando el bearer token tiene scope del proyecto y capacidad explícita de provisioning para ese mismo ID. El servidor no registra IDs arbitrarios del cliente. `init --force` remoto no está soportado en v1; resetear un DAG requiere una operación administrativa futura distinta. El endpoint tipado de init valida auth/scope/provisioning antes de crear o abrir storage y devuelve errores estructurados sin filtrar paths.

## Alternativas consideradas

| Opción | Pros | Contras |
|---|---|---|
| **API HTTP(S) tipada, implementada por un servicio Climier server-side y accesible inicialmente por Tailscale** | Conserva kernel/providers y atomicidad; controla acceso por proyecto; cliente ligero; el mismo contrato funciona en el host de prueba y detrás de DNS/TLS/cloud | Requiere ejecutar y mantener un servicio autenticado; SSH queda solo para deployment/túnel/operación inicial |
| Cliente que lee/escribe un state remoto como blob/archivo | Transporte aparentemente simple; reutiliza parte de persistencia existente | No basta con CAS para preservar locks, políticas y estado+log atómicos; propenso a claims perdidos y a replicar internals del kernel |
| Compartir filesystem remoto (NFS/SSHFS) y usar backend local | Cambios de protocolo pequeños | Locks por filesystem distribuido no son garantía suficiente; disponibilidad/permisos y latencia quedan acoplados al mount; no ofrece una frontera de servicio ni autenticación por proyecto |
| Extender la UI server existente | Reutiliza endpoints y despliegue UI | Está diseñada para un proyecto, solo GET, local-only y sin auth; mezclar dashboard con API mutante amplía demasiado su responsabilidad |
| Hacer del SSH/SFTP el protocolo de estado (leer/escribir archivos por comandos remotos) | Aprovecha el acceso Tailscale/SSH ya disponible para la prueba inicial | Acopla clientes al sistema operativo y layout remoto, no ofrece API cloud-native ni auth/aislamiento por proyecto suficientemente claros; dificulta mantener transacciones y compatibilidad de protocolo |

## Alcance

- Dentro:
  - esquema/configuración de `.climier.json` para elegir local o remoto, manteniendo compatibilidad local por defecto;
  - servicio remoto desplegable que aloja varios proyectos identificados por `project_id`, con persistencia server-side y aislamiento entre proyectos;
  - bump/migración de la versión de state y ledger monotónico por el cambio de semántica del fence CAS; el CLI anterior queda fuera de soporte para estos proyectos y el servidor rechaza protocolo incompatible; writers compatibles detectan regresiones causadas por rutas locales antiguas y fallan cerrado, mientras `restore`/`init --force` compatibles recuperan rebasing por encima del ledger;
  - journal de transferencia local con snapshot de reintento temporal en directorio privado/0600, limpieza configurable tras estado terminal y recuperación por `transfer-status`/reuso de `transfer_id`; nunca guarda credenciales dentro del snapshot transferido;
  - API remota versionada para operaciones tipadas; routing v1 según la matriz de superficies en Propuesta, incluyendo lecturas, mutaciones built-in, operaciones core/batch e init. `snapshots`, `restore` y UI remota devuelven `REMOTE_UNSUPPORTED_OPERATION` sin tocar estado local;
  - una fachada de backend en cliente para CLI/adapters y host de plugins; providers/kernel permanecen transport-neutral y el server ejecuta las operaciones en su propio kernel/storage;
  - catálogo server-side que mapea IDs opacos a storage confinado, rechazando traversal/colisiones/no autorizado; policies/plugins de autoridad se provisionan en servidor, no desde payload de cliente;
  - autenticación separada de `--as`, autorización por proyecto y transporte seguro remoto;
  - operaciones mutantes normales serializadas server-side con claims concurrentes y log+estado atómicos;
  - `push` local→remoto y `pull` remoto→local según los contratos/precondiciones JSON definidos arriba: copia entera validada, sin merge, overwrite opt-in con CAS, claims/in-progress bloquean replace, destino intacto en conflicto/error;
  - E2E inicial sobre la máquina Linux del usuario mediante endpoint HTTP(S) alcanzado por Tailscale. SSH agent puede instalar/administrar el servicio o levantar el túnel de prueba; nunca es requisito del CLI/producto, campo de `.climier.json` ni formato del protocolo; runbook sin hostnames/IPs/secrets versionados;
  - pruebas de aislamiento multi-proyecto (incluido traversal/colisión), auth, concurrencia, round-trip push/pull, CAS/overwrite, logs/revisions/claims, local compatibility, fallos de red y no-fallback para todas las lecturas, incluyendo `state`. La prueba E2E usa dos clientes: mutación de uno visible por el otro y DAG local intacto; desconexión/auth fallida no accede localmente;
  - documentación de configuración y operación cloud-portable del servicio remoto.
- Fuera:
  - sincronización eventual, cache local mutable u operación offline; `push`/`pull` son transferencias puntuales completas y explícitas;
  - replicación entre servidores, alta disponibilidad, clustering o backup externo gestionado;
  - migración automática del DAG local al iniciar/usar el backend remoto; la transferencia debe invocarse mediante `push`;
  - merge de dos DAGs divergentes, sincronización incremental/conflict resolution o copia de secretos/runtime local de plugins;
  - snapshots/export raw del servidor y restore remoto durante v1, además de UI del DAG configurado como remoto;
  - UI multiusuario, usuarios/roles completos, billing o servicio SaaS operado por el proyecto;
  - alterar semántica del DAG o del lifecycle para permitir uso remoto.

## Riesgos y open questions

- La frontera actual de storage devuelve paths locales y snapshots usan operaciones raw de filesystem → definir una fachada completa de backend compartida por los adapters/host de plugins de CLI, no hacer transport-aware el kernel ni providers. El cliente elige modo local (kernel/storage local) o remoto (API); el servidor ejecuta kernel/providers/storage localmente. `state` se incluye como lectura remota; APIs plugin no mapeadas a operaciones core tipadas no son compatibles con proyectos remotos en v1. `snapshots` y `restore` devuelven `REMOTE_UNSUPPORTED_OPERATION`, sin fallback local. `push`/`pull` tienen API específica de transferencia completa validada, nunca endpoints genéricos de archivo.
- Las políticas/plugins actualmente pueden depender de configuración y runtime locales → la autoridad de proyecto remoto corre solo en el servidor y se provisiona administrativamente; las extensiones de cliente fuera de operaciones core tipadas quedan no soportadas en v1. No transmitir secretos o código de plugin desde clientes implícitamente. `push`/`pull` no copian instalación, secretos ni runtime de plugins.
- La transferencia completa reemplaza las collections del DAG. Se conservan las entradas de log del destino; el log fuente se guarda como payload namespaced auditable dentro de un evento de transferencia con dirección, fuente, hash/revisión fuente y revisión previa/nueva destino (no se reinsertan entries fuente de primer nivel). Una repetición idéntica es no-op por hash. La revisión global y las revisiones de todos los nodos entrantes se rebased al fence `F`, incluyendo el ledger high-water del destino; nodos creados después reciben revisión basada en el siguiente `state.revision`, evitando que un CAS individual antiguo vuelva a ser válido incluso tras borrar/recrear ID. Un state por debajo del ledger no puede entrar o salir por transfer: exige recuperación compatible. El ledger sobrevive a `restore`, `init --force` y snapshots, y previene regresiones de writers compatibles; el siguiente writer compatible detecta una restauración local hecha por un binario antiguo y falla cerrado, pero no se afirma que el schema impida escrituras locales directas de ese binario. `transfer_id` idempotente resuelve timeouts de resultado desconocido. El ADR fijará los fields exactos y probará la semántica y concurrencia. Schema/protocolo incompatible y claims/tareas `in_progress` bloquean la transferencia según sus reglas de fuente/destino.
- SSH agent/Tailscale está disponible solo para la máquina de prueba y no es el target de producto → documentar setup E2E específico como entorno de verificación, pero no añadir nombres, IPs, rutas o secretos reales del host a `.climier.json`, tests o documentación versionada.
- Credencial simple inicial: ¿token bearer por servidor con scope explícito de `project_id`, o identidad/autorización más elaborada? Recomendación inicial: bearer token fuera del repo, scope por proyecto, sin convertir `--as` en autenticación.
- Alta de proyectos y ownership: ¿el servidor preconfigura un catálogo permitido o `init` provisiona un nuevo proyecto bajo permiso explícito? Evitar que cualquier token válido cree proyectos arbitrarios.
- Evolución del protocolo/state schema: definir compatibilidad entre clientes y servidor de distintas versiones y error ante incompatibilidad; no aceptar escrituras desconocidas silenciosamente.
- Disponibilidad/latencia: las operaciones mutantes deben fallar de forma visible si el servidor no está disponible; no usar estado local como fallback que pueda divergir.
- El package raíz es stdlib-only y `ui/` es un subproyecto aparte → decidir cómo distribuir/ejecutar el servicio sin añadir dependencias runtime al CLI.
- El trabajo toca fronteras compartidas y debe dividirse en entregas con evidencia observable: (1) contrato/config/backend y compatibilidad local; (2) servicio con aislamiento multi-proyecto, auth y prueba concurrente de claims; (3) routing de cada clase de comando/init con prueba de que desconexión remota no accede al DAG local, incluyendo `state`; (4) transferencia push/pull con round-trip, validación, CAS bajo lock del destino y overwrite seguro, incluyendo tests concurrentes y CAS obsoletos; (5) empaquetado, E2E en host Tailscale por API HTTP(S), operación y docs cloud-portables. Cada entrega debe tener condición de salida observable y comandos/tests de evidencia. Las pruebas de transferencia compiten con mutaciones y otras transferencias, verifican que conflicto/fallo deja destino intacto y revisión monotónica, y prueban que CAS antiguos de state/nodes no vuelven a ser válidos. El E2E en dos clientes demuestra visibilidad cruzada, copia local intacta y ausencia de fallback. La descomposición final en tasks y su evidencia detallada se fija en el ADR.
