# ADR-040: listo para publicar

- Gate: `G-v1-baseline-adr-040` · Deriva de: `G-v1-baseline-rfc` · Estado: borrador
- Fecha: 2026-09-27

## Contexto

El paquete declara `1.0.0` pero **nunca se publicó**: `npm view climier version` responde 404 y el repo no tiene tag de release (su único tag es `archive/graph-kernel-log-fields-7dd34ef`). El CI (`.github/workflows/ci.yml`) corre `npm test` y `npm run pack:check` en Node 20. El flujo de release es manual y está documentado en el README (actualizar CHANGELOG, subir versión, correr checks, mover notas, tag, publicar). El runbook del servidor remoto (`docs/remote-server.md`) existe y es detallado, pero describe el esquema anterior. La recuperación de un lock obsoleto es manual por decisión de diseño —los locks no se limpian solos, y un proceso muerto deja el archivo— y está documentada como techo conocido. El paquete no tiene dependencias de runtime: solo `oxlint` como devDependency. La suite UI está fuera del tarball (`files` incluye `bin`, `src`, README, CHANGELOG y LICENSE) pero su fuente queda en el árbol con dos lockfiles (`package-lock.json` y `pnpm-lock.yaml`).

## Decisión

1. **El corte se publica como `v1.0.0`, la primera publicación real.** Sección de release en `CHANGELOG.md` que explique en términos llanos que es la primera versión limpia, que el esquema de estado es 1, que no hay compatibilidad con formas anteriores y que hay que importar los proyectos existentes antes de usar el binario nuevo. La sección la deja la cadena de implementación; el tag `v1.0.0` lo crea el dueño al publicar (§Decisión 2). El CHANGELOG tiene hoy una sección `[1.0.0] - 2026-07-11` que **nunca se publicó** y una `[Unreleased]` con cambios reales: como no hay release previa, las tres se reconcilian en **una sola** sección `[1.0.0]` con la fecha real del corte —el contenido viejo se absorbe, no se duplica—, `[Unreleased]` queda vacía, y ninguna entrada describe un estado que nunca existió.
2. **La publicación la ejecuta el dueño, no un worker.** Publicar es una acción hacia afuera e irreversible: la cadena de implementación deja el repo listo, verificado, con la versión y la sección del CHANGELOG en su lugar, y el dueño crea el tag y corre `npm publish`. Ni el tag ni la publicación los hace un worker, y ningún paso de este ADR publica nada.
3. **CI cubre más que los tests.** `.github/workflows/ci.yml` corre `npm test`, `npm run pack:check` y una **verificación de superficies retiradas**: un chequeo que falla si reaparecen en docs, help o CI los comandos, flags y campos que este corte retira. La lista de superficies retiradas **se genera del código** —`knownFlags` de cada comando y las allowlists por kind de los providers—, no se escribe a mano desde una doc: si se escribe a mano, el check hereda el error que debería detectar. El lint global entra al CI **solo cuando cierre la campaña de ADR-035** (`T-rar-lint-global-zero`): hoy el lint no está en cero y meterlo antes rompería el CI. El job corre hoy **solo en Node 20** mientras `engines` declara `>=20`: la matriz cubre el piso declarado y el LTS vigente, o el rango se angosta a lo que realmente se prueba. Un rango de soporte declarado y no ejercitado es deuda silenciosa en la primera publicación.
4. **`prepublishOnly` con las verificaciones del release, y un smoke del artefacto instalado.** El script encadena test, lint sobre los paths del corte y `pack:check`. Pero `pack:check` es solo `npm pack --dry-run` y el e2e del servidor arranca desde el checkout: ninguno prueba el paquete **instalado**. Para la primera publicación hace falta un smoke que empaquete, instale el tarball en un prefijo temporal y ejecute los binarios instalados: `climier --version` y `climier init` contra un proyecto temporal, y `climier-server` con health y una solicitud autorizada. `prepublishOnly` no sustituye ese smoke ni protege si se publica con scripts desactivados. El smoke además ejecuta `climier ui` contra ese proyecto temporal y exige el fallo accionable del comando experimental cuando el subproyecto no está instalado —exit distinto de cero y envelope de error—, nunca un stack de resolución de módulos.
5. **Metadata de publicación revisada, sin campos de repositorio, con la documentación resuelta dentro del artefacto.** `package.json` con `description`, `keywords`, `license`, `engines`, `files` y `bin`; **sin `repository`, `homepage` ni `bugs`** (decisión del dueño: este release va sin ellos). Sobre la documentación, el criterio no es que el README nombre `docs/reference.md` —esa línea es un artefacto aguas abajo que este corte reescribe igual— sino que **el artefacto publicado debe llevar el manual que ofrece**: `docs/reference.md` es la referencia del producto y entra a `files`, y la línea del README se ajusta a lo que el artefacto realmente lleva. El resto de `docs/` sigue fuera, y la aserción de contenido del tarball (`test/package.test.mjs:15-35`) pasa a exigir `docs/reference.md`.
6. **El runbook del servidor remoto se actualiza al esquema v1 y al orden operativo**, y el import deja de ser una nota: el runbook y las notas del release llevan los pasos ejecutables —instalar o enlazar primero el binario v1, detener todos los escritores (control plane, UI y el servidor remoto antes de migrar su `stateHome`), `climier migrate --all --dry-run`, `climier migrate --all`, y el comando de verificación por proyecto— más la advertencia de que un binario previo al corte sobre un proyecto migrado puede sugerir `init --force` y borrar datos. También el procedimiento de recuperación de lock obsoleto con su criterio de verificación, y cobertura del caso. El runbook incluye además **el camino de vuelta**: con el binario nuevo ya enlazado y los proyectos migrados, revertir significa restaurar los respaldos por proyecto con los escritores detenidos y volver al binario anterior, en ese orden; sin ese procedimiento escrito, la ventana operativa no tiene plan B. Y el corte se **ensaya completo sobre una copia del parque entero** —`CLIMIER_HOME` copiado, no solo los dos proyectos de volumen—: enlazar → detener → dry-run → migrar → verificar → revertir, con la copia como evidencia del ensayo.
7. **Checklist de release verificable.** Una lista corta y ejecutable (suite verde, lint del corte verde, `pack` verificado, CHANGELOG con la sección, tag, import guiado, smoke local del CLI y del servidor) que cualquier persona pueda seguir sin leer este ADR.
8. **`climier ui` entra como experimental, y no se publica roto.** Decisión del dueño: el comando se queda en el producto y va a seguir cambiando, así que se etiqueta **experimental** en el help, `README.md` y `docs/reference.md`. Pero `files` excluye `ui/` mientras incluye `src/cli/commands/ui.mjs`, que busca el subproyecto adyacente y sus dependencias: hoy, en una instalación publicada, el comando aparece en el help y revienta con un error de resolución de módulos. El corte no puede dejarlo así: el comando detecta que faltan `ui/server/server.mjs` o las dependencias del subproyecto y falla con un envelope de error accionable —exit distinto de cero— que dice cómo habilitarlo. La etiqueta experimental y el fallo accionable reemplazan al "no verificado"; la fuente, su `package.json` y sus dos lockfiles no viajan al tarball. Si el subproyecto está presente pero el estado no es legible por el binario, el comando propaga el error del binario en vez de fallar a mitad de camino.

## Consecuencias

- A favor: por primera vez el proyecto tiene un artefacto publicable, verificado y reproducible, con un runbook que describe el esquema que realmente existe.
- A favor: la verificación de superficies retiradas convierte "no quiero v2 ni nada" en algo que el CI sostiene, no en una promesa de la documentación.
- En contra / deuda: una publicación real es irreversible; a partir de ahí la semántica de versión importa y este ADR solo cubre la primera.
- En contra / deuda: la incorporación del lint al CI queda dependiente de otra campaña (ADR-035), así que el CI queda completo recién cuando esa cierre.

## Plan de implementación

1. **Verificación de superficies retiradas** — archivos: script de verificación (nuevo) y `.github/workflows/ci.yml`. Falla si reaparecen comandos, flags o campos retirados.
2. **CI con las verificaciones nuevas, matriz de Node y smoke del artefacto** — archivos: `.github/workflows/ci.yml`, `package.json` (`prepublishOnly`), script de smoke del tarball instalado. Matriz en el piso declarado y el LTS vigente, o `engines` angostado a lo que se prueba. Bloqueada parcialmente por el cierre de la campaña de lint (ADR-035) para la parte de lint.
3. **Metadata de publicación y documentación publicada** — archivos: `package.json`, `README.md`. Revisión de campos, contenido del tarball y destino de la documentación.
4. **CHANGELOG y notas de release** — archivos: `CHANGELOG.md`. Sección del corte, guía de import, lista de flags y campos retirados con su reemplazo, y reconciliación de la `[1.0.0]` existente y de `[Unreleased]` en una sola entrada con la fecha real.
5. **Runbook alineado al esquema v1 y a la importación obligatoria** — archivos: `docs/remote-server.md`, `README.md`, `CLIMIER-CHEATSHEET.md`, `AGENTS.md`, `docs/reference.md`. La publicación depende de que estos queden coherentes con el import: hoy README y `docs/reference.md` dicen v3/v2 y mandan `init --force` para el v1 prehistórico, el cheatsheet dice v2 y AGENTS dice v3. Orden operativo, advertencia sobre binarios previos, recuperación de lock obsoleto, camino de vuelta por respaldos y checklist de release. Disposición explícita de `docs/plans/*` y `.evidence/` en el mismo commit: archivar o borrar, decidido y justificado, sin dejarlos como documentación zombi de un producto que ya no existe.
6. **`ui` experimental y fallo accionable en el artefacto** — archivos: `src/cli/commands/ui.mjs`, `src/cli/dispatch.mjs` (help), `README.md`, `docs/reference.md`, más el smoke de la pieza 2. Etiqueta experimental y detección de dependencias faltantes. La fuente del subproyecto, su `package.json` y sus dos lockfiles quedan como están y fuera del tarball: en este corte no se consolidan ni se retiran.

## Verificación

- `npm test`, `npm run pack:check` y la verificación de superficies retiradas pasan en CI sobre un push de prueba.
- `npm pack --dry-run` lista `bin`, `src`, `docs/reference.md`, README, CHANGELOG y LICENSE, y nada de `test/`, `ui/`, `.agents/` ni `AGENTS.md`.
- `npm publish --dry-run` no falla por metadata faltante, y el `package.json` no declara `repository`, `homepage` ni `bugs`.
- `climier ui` sobre una instalación del tarball falla con el envelope de error accionable y exit distinto de cero; el help lo presenta como experimental.
- El CHANGELOG tiene una sección `v1.0.0` con la guía de import y la lista de retiros.
- El CHANGELOG tiene una sola sección `1.0.0` con la fecha real del corte, `[Unreleased]` vacía, y ninguna entrada describe un estado que nunca existió.
- El CI corre en el piso declarado y en el LTS vigente de Node, o `engines` declara exactamente lo que se prueba.
- El corte se ensayó completo sobre una copia del parque entero, incluida la reversión por respaldos, y la copia queda como evidencia del ensayo.
- El commit del corte y la sección del CHANGELOG quedan listos para taggear; el tag `v1.0.0` y el `npm publish` los corre el dueño.
- `docs/remote-server.md` describe el esquema v1 y el orden operativo; un lector que siga el runbook desde cero levanta el servidor y conecta un cliente.
- La recuperación de lock obsoleto está documentada con su criterio de verificación y cubierta por un test.
