# ADR-035: política Oxlint por paths tocados y cierre del baseline

- Gate: `G-rar-modular-organization-adr-035` · Deriva de: `G-rar-modular-organization-rfc` · Estado: aprobado
- Fecha: 2026-09-26

## Contexto

El RFC reemplaza shards indiscriminados por verificación ligada a responsabilidad real. El baseline de Oxlint 1.85.0, ejecutado con `npm run lint` (`oxlint src bin test`), es de 1.078 errores en 105 rutas con diagnósticos, de 306 archivos analizados, y cero advertencias. El subproyecto independiente `/ui/` queda excluido por configuración; los tests `test/ui-*.test.mjs` viven en el árbol raíz `test/` y siguen dentro del alcance de lint, aunque su ejecución con `npm run test:ui` se gestione separadamente. Archivos grandes pueden empezar con deuda no relacionada con la slice, por lo que exigirles cero desde el primer cambio haría inviables tareas pequeñas; a la vez, permitir baseline sin medición ocultaría regresiones.

RFC fuente: `.decisions/G-rar-modular-organization-rfc.md`.

## Decisión

1. Para cada task que edite, mueva, cree o borre código/tests, la aceptación lista los paths fuente y destino exactos y ejecuta Oxlint 1.85.0 con la configuración del repo sobre esos paths.
2. Antes del cambio se guarda evidencia JSON de Oxlint 1.85.0 para cada source y destino preexistente declarados, tomada del commit base antes de editar. Después se lint-ean todos los sources supervivientes y destinos. Para `git mv`/split, la task adjunta una tabla por ocurrencia que mapea cada finding baseline no exceptuado a exactamente un finding final con el mismo `code` y `severity`; cada fila identifica ancla estable (test/function/helper/símbolo de producción), fragmento o fingerprint y ordinal, además del path final permitido. La atribución de cada test, símbolo o helper movido es única: un helper compartido se conserva en un solo owner/destino; no se copia a varios destinos generando findings duplicados. El split HTTP centraliza `withApi`, `authHeaders` y `operation` en `test/server/http/fixtures.ts`; ese path se declara en el owner estructural `T-rar-mod-test-server-http` y después en su cleanup exclusivo `T-rar-lint-residual-server-http`. El cambio de ownership debe quedar explícito en el diff y la tabla. Ningún finding final se reutiliza y ningún finding final queda sin pareja. Los destinos preexistentes se comparan con su propio baseline y no pueden empeorar. Los destinos nuevos no pueden añadir findings sin origen en el baseline declarado de la unidad estructural.

   Para un source predeclarado en una task estructural aprobada bajo ADR-033 (extracción de código/símbolos de producción) o ADR-034 (split de tests completos), la única excepción de esta política es disponer una ocurrencia baseline `eslint(max-lines)`/`error` atribuible a esa unidad estructural. El baseline debe exceder 350 líneas efectivas según Oxlint 1.85.0 y `.oxlintrc.json` sin cambios (`skipBlankLines`/`skipComments` efectivos). Se miden todos los sources supervivientes y destinos. En ADR-033 el source conserva la fachada/entrypoint requerido por ese ADR y el diff/tabla atribuye cada símbolo extraído a un solo destino; en ADR-034 el source puede sobrevivir, renombrarse o borrarse si el multiconjunto exacto de casos `test()` se conserva y cada test completo se mueve exactamente una vez. En ambos casos, el diff debe probar que la reducción procede de la extracción/movimiento estructural declarado, no de borrar o reescribir código/tests, cambiar expectativas, renombrar para ocultar deuda, añadir suppressions o cambiar configuración. Un destino preexistente se compara con su propio baseline y no puede empeorar; un destino nuevo no puede exceder 350 líneas salvo que sea el único destino final que herede, por mapping 1:1, esa misma ocurrencia baseline `max-lines`.

   La tabla marca explícitamente la fila baseline de `max-lines` con path y conteo efectivo antes/después: si ningún source/destino final reporta esa ocurrencia, se registra «resuelto por split estructural» y no se asigna a cleanup; si exactamente un archivo final la conserva, no se declara extinción, se mapea 1:1 como deuda heredada y se asigna un cleanup owner; si varios archivos finales presentan findings atribuibles a la misma ocurrencia, se rechaza el split por fan-out. Si la extracción no está predeclarada bajo ADR-033/034, no hay carve-out y se exige mapping sin pérdidas. No se exceptúa ningún `eslint(max-lines-per-function)`, otra ocurrencia sin evidencia o finding nuevo.

   Los nombres de casos `test()` deben conservar su multiconjunto exacto, incluyendo duplicados, entre el source base y la unión de sources supervivientes y destinos. Registrar `node --test <source>` ejecutado en el commit base antes del movimiento, y después ejecutar cada source que sobreviva más cada destino; no intentar ejecutar en el diff final un source borrado o renombrado. Cada test/símbolo/helper movido se atribuye una sola vez; código/casos realmente añadidos o modificados deben quedar en cero diagnostics. La excepción no permite arreglos incidentales de lint ni cambios de comportamiento. El cleanup residual y el cierre global siguen cubriendo toda deuda restante según los puntos siguientes.

Toda deuda heredada que quede en sources/destinos tocados se añade explícitamente al backlog de cleanup residual después de completarse el slice estructural. El ownership de un path es exclusivo en cada momento: la task estructural posee sus sources/destinos durante el split y la validación; solo después de aceptarse la task, el cleanup dependiente recibe ownership exclusivo de los paths residuales y los lleva a cero. No hay ownership simultáneo entre split y cleanup, aunque ambos actúen secuencialmente sobre un path. Una tabla/checklist de cobertura relaciona cada finding baseline no marcado explícitamente «resuelto por split estructural» bajo §Decisión 2 con exactamente un owner de cleanup; no hay otras excepciones de deuda no incluida. No se puede declarar cubierto el global mientras haya findings sin owner.
3. Si el propósito explícito de una task es limpiar Oxlint de una unidad/path, la aceptación exige cero diagnósticos en esos paths (incluye deuda preexistente de esa unidad). Tareas de organización/refactor no asumen limpiado global incidental fuera de su slice.
4. Workers registran comando, versión, conteo inicial/final por regla/severidad/path y pruebas ejecutadas en la nota de submit. Captura reproducible desde la raíz: `./node_modules/.bin/oxlint --version` debe informar `1.85.0`, después `./node_modules/.bin/oxlint --format json -c ./.oxlintrc.json <paths>`; comparar diagnósticos por `(filename, code, severity)`. No se permite suppression nueva, desactivar reglas ni cambiar configuración para ocultar deuda; las exclusiones de rutas explícitas y revisables (por ejemplo excluir el subproyecto `/ui/` del universo lint) requieren actualizar este ADR y no pueden excluir paths dentro del scope declarado de `test/`. No se permite autofix masivo para ocultar deuda. Autofix localizado puede usarse solo tras revisar diff y tests si no altera contrato.
5. ADR-033 y ADR-034 bloquean sus tasks de implementación hasta que ADR-035 se apruebe; cada task lista los gates ADR aplicables más ADR-035. Las tasks de limpieza también bloqueadas por ADR-035. La deuda de un path la posee una task a la vez.
6. Crear tasks de limpieza de diagnóstico con ownership exclusivo y acceptance cero por scope. Cubren findings por paths no modificados estructuralmente y todos los findings residuales heredados de los paths fuente/destino de las slices estructurales. La lista de residuos se calcula después de cada slice (destinos incluidos) y se añade con IDs de tasks cleanup y paths exactos. Dividir por directorios/path groups para permitir paralelismo. El plan final enumera tanto tasks estructurales como cleanup residual por cada finding original, antes del global. La única excepción requiere resolver `G-rar-transaction-size-debt` mediante una enmienda explícita de este ADR: `T-rar-lint-transaction-nonsize` puede cerrar habiendo limpiado todos los findings no-size y transfiriendo los tres findings de tamaño enumerados en esa enmienda al cierre global; no puede declarar `src/kernel/transaction.mjs` limpio, y la aceptación global debe informar esos findings como no-cero.
7. El cierre global es un task distinto, dueño de `src bin test` sujeto a las exclusiones de configuración (incluida `/ui/`); `test/ui-*.test.mjs` permanece dentro del scope. Está bloqueado por todas las tasks estructurales, todas las tasks de cleanup por scope y `G-rar-transaction-size-debt`. En la ruta predeterminada debe ejecutar `npm run lint` con Oxlint 1.85.0 y exigir cero errores y advertencias; reporta rutas analizadas, rutas con diagnósticos y total. Solo una enmienda explícita aprobada de este ADR bajo `G-rar-transaction-size-debt` puede diferir los tres findings de tamaño de `src/kernel/transaction.mjs`; si se aprueba esa excepción, el cierre debe enumerar los findings exactos y reportar el resultado no-cero, nunca llamarlo «cero» o limpio. La ejecución de tests UI no es criterio de este cierre lint.

   **Enmienda aprobada por `G-rar-transaction-size-debt` (2026-09-27):** se difieren exclusivamente los tres findings estructurales actuales de `src/kernel/transaction.mjs`: `eslint(max-lines)` sobre el archivo (377 líneas efectivas; máximo 350), `eslint(max-statements)` sobre `createTransaction` (33; máximo 20) y `eslint(max-lines-per-function)` sobre `createTransaction` (312 líneas; máximo 40). La revisión arquitectónica concluyó que mover la normalización/clonado del snapshot o la validación de edges podría reducir las dos primeras métricas, pero no la función extensa; extraer accessors que cierran sobre los maps mutables compartidos violaría ADR-033 §Decisión 5 si se hace solo por contadores de tamaño. `T-rar-lint-transaction-nonsize` conserva ownership exclusivo de `src/kernel/transaction.mjs` hasta aceptación y debe limpiar todos los hallazgos no-size, sin declarar el archivo limpio. Después, el cierre global puede reportar exactamente estos tres errores y cero advertencias; cualquier otro diagnóstico hace fallar el cierre. El resultado global es no-cero y no puede denominarse «cero» ni limpio.
8. La activación del lint en CI no forma parte de este ADR ni ocurre automáticamente al llegar a cero; requiere una decisión posterior.
9. Los findings contractuales baseline descubiertos durante modularización (por ejemplo recovery → commit → read de ledger) se crean y corrigen como tasks de comportamiento independientes, con test rojo primero, antes del split que dependa de esa semántica.

## Consecuencias

- A favor: cada worker demuestra el efecto de su cambio y reduce deuda relevante sin bloquear slices por findings ajenos; queda separado el control focal del cierre de baseline global.
- En contra / deuda: requiere evidencias baseline/final consistentes y una tarea de cierre explícita; las tasks estructurales pueden terminar con findings históricos no modificados, aunque el objetivo global siga siendo cero.

## Plan de implementación

1. Aprobar ADR-035 antes de crear tasks: toda task de implementación/cleanup se bloquea por ADR-035 y por el gate funcional aplicable.
2. Materializar slices estructurales con ownership paths exclusivo y acceptance de no-regresión; al aceptar cada una, actualizar el inventario de findings residuales y crear cleanup tasks cero por paths bajo ADR-035. Así se incluyen explícitamente residuos en módulos/suites que la slice dejó intactos.
3. El task global `src bin test` se crea después y queda bloqueado por todos los IDs estructurales y cleanup, además de `G-rar-transaction-size-debt`. Antes de iniciarlo, la decisión de ese gate determina su acceptance: si se elige una ruta arquitectónica permitida, validada y compatible con ADR-033 que elimine los tres size findings de `transaction.mjs`, el lint global exige exit 0 y cero errores/advertencias; si una enmienda explícita de ADR-035 difiere esos findings, se actualizan el nombre/acceptance del task para enumerarlos y reportar el resultado como no-cero, nunca como «cero» o limpio. La mera resolución del gate no altera la acceptance por sí sola. Los tests UI del árbol raíz continúan lint-eados, pero ejecutar `npm run test:ui` no forma parte del cierre global.
4. Evaluar la activación de CI en una decisión separada una vez aceptado el cierre global.
5. El owner residual de cada unidad estructural es una task con paths exclusivos, acceptance Oxlint cero y dependencia del split que origina su baseline; su ID se añade como blocker de `T-rar-lint-global-zero` antes de que pueda correr el cierre. Cada excepción o deuda arquitectónica requiere un gate explícito aparte y no permite que el cierre global informe cero si persisten diagnósticos. Para `src/kernel/transaction.mjs`, resolver `G-rar-transaction-size-debt` es requisito antes de iniciar `T-rar-lint-global-zero`: si ADR-033 §5 se mantiene, la decisión debe definir una vía arquitectónica permitida que quite los tres findings; si se enmienda el criterio global para diferirlos, el cierre no puede llamarse «cero». `T-rar-lint-transaction-nonsize` no es allowlist y sigue bloqueado por ese gate.

## Onboarding breve para crear tasks

- [x] No hace falta otro onboarding — el comando exacto (`npm run lint`), versión, alcance, baseline observado, política por path y condición global de cierre están definidos; las tasks de implementación solo deben añadir sus paths/runner y evidencia.

## Verificación

- Para cada task, se comprueba `./node_modules/.bin/oxlint --version` = `1.85.0`; se guardan JSON del commit base para cada source y destino preexistente, y JSON final para todos los sources supervivientes y destinos, usando `./node_modules/.bin/oxlint --format json -c ./.oxlintrc.json <paths>`. Un source borrado/renombrado se ejecuta y captura en su commit base; no se invoca por su path ausente en el diff final. Splits requieren tabla por ocurrencia con `code`, `severity`, ancla, fingerprint/ordinal y path final; no alcanza comparar solo conteos agrupados por `(filename, code, severity)`. Se reportan conteos por regla/severidad/path y líneas efectivas para `max-lines`.
- Ninguna task añade hallazgos no explicados; cada destino nuevo se queda ≤350 líneas salvo la única ocurrencia `max-lines` heredada y mapeada según §Decisión 2, y los casos/código realmente añadidos o editados quedan limpios; los destinos preexistentes no empeoran respecto de su propio baseline. La excepción `max-lines` solo aplica con la evidencia por unidad estructural indicada en §Decisión 2. Las tasks de limpieza focal terminan en cero para su scope declarado.
- Cada finding que quede tras un slice estructural tiene un cleanup owner ID/path antes de poder crearse el task global; el task global bloquea por todas las tasks estructurales y de cleanup. Una ocurrencia `max-lines` solo queda fuera de cleanup si su fila está explícitamente marcada «resuelto por split estructural» conforme a §Decisión 2; no hay allowlists por task sin evidencia.
- `T-rar-lint-global-zero` no puede iniciarse hasta que esté resuelto `G-rar-transaction-size-debt` y se haya actualizado su acceptance según la decisión. Si se aprueba una ruta permitida y verificada que retire los tres size findings de `src/kernel/transaction.mjs`, el cierre exige cero. Si una enmienda explícita de ADR-035 difiere los tres, el cierre documenta esos diagnostics exactos y su resultado no-cero sin llamarlo «cero» o limpio. La mera existencia/resolución del gate no es un waiver.
- En cierre, `npm run lint` ejecuta Oxlint 1.85.0 en `src bin test` con `/ui/` excluido por `ignorePatterns` y mantiene incluidos todos los tests bajo `test/` (incluidos los catorce `test/ui-*.test.mjs` de raíz); no requiere ejecutar `npm run test:ui`. Si el gate de transaction elige la ruta arquitectónica a cero, el cierre devuelve cero diagnósticos; si ADR-035 se enmienda para diferir los tres size findings, el cierre reporta el resultado no-cero y esas rutas/reglas explícitamente, sin denominarlo cero. La deuda baseline de esos catorce archivos raíz tiene cleanup owner `T-rar-lint-test-ui-files`, que valida Oxlint sin ejecutar las suites. Los cuatro destinos y el helper común predeclarado del split provider-knowledge tienen cleanup owner `T-rar-lint-residual-provider-knowledge`; `test/providers/task/task-fixtures.ts` pertenece a `T-rar-lint-residual-provider-test`; `test/server/http/fixtures.ts` y `test/cli-operation-bridge-matrix.test.mjs` pertenecen a `T-rar-lint-residual-server-http`; y `test/kernel/mutation/helpers.ts` pertenece a `T-rar-lint-residual-kernel-tests`. Cada owner está bloqueado por su split y ADR-035, posee cada path/helper una sola vez, y figura como blocker explícito de `T-rar-lint-global-zero`.
- No se habilita CI sin decisión separada.

## Enmienda (v1-baseline, T-v1-ui-delete)

El slice 5 de ADR-039 eliminó la suite UI raíz (`test/ui-*.test.mjs`,
`test/jsx-loader.mjs`, `test:ui` y el andamiaje JSX/overview), así que las
decisiones 6, 7 y el apartado de cierre de este ADR ya no incluyen esos paths:
el cierre global de lint cubre `src bin test` sin los catorce archivos UI, que
dejaron de existir. `T-rar-lint-test-ui-files` se canceló y su deuda dejó de
formar parte del blocker de `T-rar-lint-global-zero`, cuyo baseline se anotó
con esta actualización. La partición por scope de los demás owners sigue igual.
